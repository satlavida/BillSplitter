### Realistic item-add load: 10 sessions x 5 bills x 10 items

Simulates several sessions each with several bills getting items added around
the same time — the shape that actually matters for this app, vs. one bill
taking thousands of sequential inserts. Requests interleaved across all
bills and fired at concurrency 50 via a custom curl+xargs driver
(not `hey`, which only targets one URL per run).

**Requests/sec here is a client-side driver ceiling, not the server's
capacity** — this driver forks a bash+curl process per request, and on this
machine that alone caps out around 250-300 req/s even against a no-op
`GET /healthz` (measured directly, no server work at all). Trust the
**p50/p90/p95/p99 latencies** (each is curl's own per-request timing, not
inflated by scheduling overhead before the request starts) and the **error
count** as the real signal from this benchmark; for a true throughput
ceiling on one endpoint, use `hey` directly (see bench_add_item.sh, which
hit ~3,000-5,000 req/s on AddItem — this app's real capacity is nowhere
near this driver's ~300 req/s limit).
